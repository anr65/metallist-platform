# Исправление номера карты операционистом

Дата: 2026-09-21.

Владелец процесса разрешил операционисту исправлять полный номер существующей активной карты на production. Операционист выбирает карту по маске, вводит новый полный номер и причину. Изменение доступно также главному администратору. С 21.09.2026 операционисту также разрешено создавать новую карту: выбрать существующий банк, ввести ФИО владельца и полный номер. Создание карты не создаёт проводок, полный номер сохраняется в зашифрованном хранилище, обычный API возвращает только маску, действие записывается в аудит. Создание банка и первоначальное дозаполнение номера ранее заведённой карты остаются у главного администратора. Для нового права миграция схемы не требуется.

Исправление запрещено, если карта уже фигурирует в запросе на карты, реестре оплат, бухгалтерских проводках или наблюдениях остатка. Иначе изменение номера могло бы изменить ранее отправленный XLSX или смысл учётной истории. Пользователь получает явную ошибку; такую карту нужно разбирать отдельным процессом, а не переписывать реквизиты задним числом. `expected_mask` защищает от исправления не той карточки после изменения списка.

Миграция 009 после версии 008 добавляет `cards.pan_ciphertext bytea NULL` и ограниченное право обновлять маску, последние четыре цифры и шифртекст для production-роли приложения. Старые зашифрованные файлы остаются доступны без миграции данных. При исправлении новый PAN шифруется существующим ключом, а маска, шифртекст и запись аудита публикуются одной транзакцией. После успешного commit прежний зашифрованный файл удаляется; если удаление не удалось, ошибка попадает в журнал без PAN и требует ручной очистки. Полный номер не возвращается в API и не попадает в аудит.

Перед production-применением: проверить точный хост и версию схемы 8, создать и проверить свежий backup базы, каталога PAN и ключа; восстановить отдельную копию БД и применить миграцию на ней. Затем применить 009 к рабочей БД одной транзакцией, проверить версию, права роли, число карт и ledger. Новое приложение запускать только после миграции. При неуспешном запуске вернуть предыдущий релиз; существующие карты без исправлений продолжают работать. После первого исправления откат на старый бинарник недопустим: он не читает `pan_ciphertext`; использовать исправленный новый релиз. Дамп БД и ключ должны восстанавливаться вместе.
