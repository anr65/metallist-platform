# Миграция 003: Telegram-сборщики

Статус: проверена на одноразовой локальной БД; к `metallist_demo` не применена
Дата: 2026-09-14

## Назначение

`schema/003_telegram_collectors.sql` добавляет роль `collector`, уникальную связь пользователя с хранителем наличных, защищённое сохранение Telegram update и краткоживущий выбор команды из меню. Существующие `users`, `drafts`, проводки и балансы не переписываются. Новые поля nullable; ранее развёрнутая версия приложения может работать после добавления схемы до переключения кода. Публикация кнопкой использует прежний immutable ledger и ключи идемпотентности.

## Проверенная тестовая цель

Локальная disposable PostgreSQL `metallist_platform_test` на `127.0.0.1:55434` с ролью `metallist_qa`, `APP_ENV=testing`, отдельными учётными данными и явным `TEST_DATABASE_URL=DATABASE_URL`. Проверен полный цикл: свежая копия `metallist_demo` восстановлена только в эту тестовую БД с `--no-owner --no-acl`; до миграции совпали `2` пользователя, `1` черновик, `3` реестра, `10` journal entries, `26` postings, нулевой общий дисбаланс и версия `2`. Миграция 003 выполнена в одной транзакции с `ON_ERROR_STOP=1`; после неё версия `3`, счётчики и дисбаланс не изменились. Тесты Telegram и полной системы запускаются только там.

## Условия для демо

До изменения `metallist_demo` требуется отдельное разрешение владельца именно на миграцию 003 этой базы и исправление прикладных прав роли `metallist_demo_app`. Затем повторно проверить `APP_ENV=demo`, `current_database()=metallist_demo`, `current_user`, версию 2 и текущий нулевой дисбаланс ledger. Уже создана свежая закрытая копия `/var/backups/metallist-platform/metallist_demo_before_telegram_20260914T142448Z.dump` (135 326 байт, права `0600`), проверена `pg_restore -l` и фактически восстановлена в локальную одноразовую `_test` БД с точным совпадением счётчиков. Непосредственно перед разрешённой миграцией повторить проверку, что демо не изменилось с момента копии. При любом несовпадении остановиться и создать новую проверенную копию.

В действующем demo у `metallist_demo_app` сейчас только `SELECT, INSERT` на `users`, `drafts`, `registries`, `tariffs`, и нет прав на будущую `telegram_dialogs`. Это блокирует не только новый бот, но и уже существующие подтверждения и смену пароля. В той же разрешённой транзакции после 003 предоставить только требуемые права: `UPDATE(password_hash,telegram_id,custodian_id)` на `users`; `UPDATE(status,payload,confirmed_by,confirmed_at,confirmed_amount_cents)` на `drafts`; `UPDATE(status,commission_cents,rate_bp,confirmed_at,manual_rate_bp,manual_reason,manual_approved_by,manual_approved_at,version)` на `registries`; `UPDATE(active)` на `tariffs`; `SELECT,INSERT,UPDATE,DELETE` на `telegram_dialogs`. Проверить их через `has_column_privilege`/`has_table_privilege` для точной прикладной роли. Эти права не дают изменять неизменяемые `journal_entries`, `postings` или `audit_events`.

После выполненных условий применить 003 к точной `metallist_demo` одной транзакцией, проверить версию 3 и неизменность количества/суммы проводок. Только затем развернуть код по точному SHA; скрипт развёртывания сам миграции не запускает. До появления перевыпущенного токена в закрытом файле и отдельного webhook-секрета бот останется выключен. После настройки путь задаётся `TELEGRAM_BOT_TOKEN_FILE`, секрет — в закрытой конфигурации; сервис при запуске зарегистрирует команды и webhook. Старый опубликованный токен не использовать.

Откат кода к прежнему SHA возможен без удаления новых nullable-колонок и таблицы диалогов. Если после миграции уже проведены Telegram-операции, их не удалять и не откатывать схему; исправления денег — только сторно и новое событие. Полное восстановление из backup допустимо только как отдельная согласованная операция с оценкой событий после копии.
