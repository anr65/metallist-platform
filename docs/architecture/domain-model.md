# Доменная модель

Статус: проект
Дата: 2026-09-11

## Участники и справочники

- `User`: пользователь системы и его статус.
- `Role`: набор разрешений.
- `Merchant`: мерчант и параметры расчётов.
- `MerchantTariff`: процентная ставка мерчанта с двумя знаками после запятой для расчёта комиссии от общей суммы подтверждаемого реестра; денежный результат округляется до копейки по `ROUND_HALF_UP` (`49,3850 → 49,39`).
- `Bank`: нормализованный банк.
- `Card`: внутренний ID карты, банк, отображаемая маска/последние цифры, ФИО владельца и защищённая ссылка на полный PAN. Полный PAN не хранится в основной таблице или audit log. Четыре подтверждённых вида лимитов и открытые параметры описаны в [правилах карт](../to-be/cards-and-limits.md).
- `Custodian`: конкретное лицо или место, ответственное за деньги. Каждый сборщик имеет отдельный ID и расчётный остаток; связь с `User` не обязательна, если сборщик не входит в систему.
- `ExpenseCategory`: управляемая категория расхода.

## Документы и группировки

- `MaterialBatch`: набор карт, предоставленный мерчанту.
- `SourceDocument`: оригинальный файл, сообщение или ручной отчёт.
- `ImportBatch` и `ImportRow`: результат версии parser для XLSX или банковского CSV; повторяющиеся карта и сумма не сливаются автоматически.
- `MerchantRegistry` и `MerchantRegistryItem`: бизнес-документ мерчанта.
- Для отдельного уже загруженного `MerchantRegistry` допустима разовая процентная ставка с основанием договорённости; главный администратор назначает и подтверждает её до отдельного подтверждения им фактических поступлений. Исключение привязано к ID этого реестра, помечено как ручная ставка, не изменяет общий `MerchantTariff`, не переходит на другой реестр и не пересчитывается при последующей смене общего тарифа задним числом. Резервирование ставки на абстрактный будущий реестр не требуется; форма хранения признака — технический проект.
- Подтверждённый реестр хранит ссылку на применённую версию тарифа и расчёт комиссии (техническое предложение для воспроизводимости).
- `Attachment`: ссылка на защищённый объект.

## События

- `MerchantFunding`;
- `Withdrawal`;
- `CardBalanceObservation`;
- `CashHandover`;
- В первом релизе доставка через сборщика-посредника не создаёт отдельный `CashHandover` между сборщиками: для ledger это одна передача исходный сборщик → главный администратор после подтверждения фактически полученной суммы. Физический маршрут не моделируется как цепочка хранителей; подтверждённая недостача относится на исходного сборщика А, не посредника Б;
- `CashShortage`: отдельное подтверждение недостачи у конкретного хранителя с основанием, подтверждающим и ссылкой на расхождение;
- `ShortageWriteoff`: отдельное решение главного администратора о списании невзыскуемой дебиторки сборщика в расход;
- `CashSurplus`: отдельно подтверждённый излишек наличных у фактического хранителя; до выяснения причины отражается как невыясненное поступление;
- `CashSurplusResolution`: утверждённая главным администратором классификация ранее подтверждённого излишка после установления источника; для источника «деньги мерчанта» хранит `merchant_id` и переводит невыясненное обязательство в отдельный долг этому мерчанту, не затрагивая обычный долг по реестрам и наличные;
- Для источника «погашение недостачи сборщика» `CashSurplusResolution` хранит ссылки на конкретного сборщика и его `CashShortage`; только доказанная связь с ещё открытым долгом позволяет переклассифицировать `2300` в погашение дебиторки, без нового прихода наличных. Возврат уже списанного долга и исправление ошибочной недостачи — отдельные типы решения;
- Повторная фактическая выдача мерчанту по такому resolution — отдельный `MerchantRepayment` с назначением «возврат найденного излишка»; она списывает наличные и погашает только долг, возникший из данного resolution, без автоматического зачёта обычного долга;
- `MerchantRepayment`;
- `TariffRecalculation`: отдельный предварительный расчёт затронутых реестров и финансового баланса для ставки, назначенной задним числом; публикация корректировок только после подтверждения главным администратором (форма сущности — проект);
- `Expense`;
- `CommissionAccrual`;
- `AdminInjection`;
- `ReceivableCollection`: подтверждённое фактическое поступление денег по конкретной дебиторке; ещё не списанная часть уменьшает долг без нового дохода, ранее списанная в расход часть признаётся прочим доходом периода получения со ссылкой на исходное списание;
- `CardTransfer`;
- `OutsourceOperation`;
- `OpeningBalanceBatch`.

События независимы. Не создаётся один огромный объект со статусом `FUNDED → WITHDRAWN → RETURNED`, потому что суммы разных пополнений могут смешиваться и сниматься частями.

`MerchantRepayment` относится к `Merchant` и не содержит обязательной ссылки на `MerchantRegistry`: возврат не распределяется по реестрам. При сторно реестра уже проведённые возвраты сохраняются; расчётная позиция мерчанта переклассифицируется между кредиторкой и дебиторкой согласно [правилам проводок](../accounting/posting-rules.md).
