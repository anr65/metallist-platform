# Импорт реестров XLSX и банковского CSV

Статус: проект
Дата: 2026-09-11

## Поток

```text
received → parsed → validated → previewed → approved → applied
```

Поддержка CSV добавляется как отдельный версионированный parser, не путём переименования файла в XLSX. Первый образец описан в [форматах AS IS](../as-is/source-data-formats.md#полученный-csv-банка-образец-05082026): `Windows-1251`, `;`, строка метаданных, строка заголовков, затем платежи. Это один образец, другие шаблоны требуют новых fixtures и явного mapping.

## Профили мерчантов

Тип разбора выбирается только из активного профиля выбранного мерчанта, а не из имени файла или пользовательского параметра. Версия parser сохраняется вместе с исходным документом.

| Мерчант | Parser | Файл | Статус |
|---|---|---|---|
| Наркоман | `narkoman_avangard_xls_v1`, версия 2 после миграции 025 | XLS | выписка Авангарда; однозначное сопоставление карты в выбранном запросе |
| Света | `sveta_cards_xls_v1`, версия 5 после миграции 022 | XLS / XLSX | карточная выгрузка, выгрузка по ФИО, заполненный ответ «Карты к оплате» |
| Толя | `tolya_operations_xlsx_v1` | XLSX | структура распознаётся; применение блокируется без карточного реквизита |
| Катя | `katya_payouts_xlsx_v1` | XLSX | настроен по образцу |
| Алитен | `aliten_bank_csv_v1` | CSV Windows-1251 | прежний банковский parser закреплён за мерчантом |
| Юра, Дима, Сережа | — | — | ожидается образец; загрузка заблокирована |

Света: поддерживаются прежний XLS с колонкой `По номеру карты` и XLSX без номера карты, где источником сопоставления служит ФИО из `Информация`. Источник суммы-кандидата — `Сумма`, внешней ссылки строки — `Номер вх.`. Для формата по ФИО пользователь обязательно выбирает карточный запрос того же мерчанта. Система нормализует регистр, пробелы и `ё/е`, затем автоматически связывает строку только с одним точным ФИО внутри выбранного запроса. Отсутствующее или повторяющееся ФИО оставляет строку с ошибкой. Катя: принимаются только строки со статусом `оплачена`; сумма-кандидат — `Выплата`, банковская комиссия хранится отдельно, внешний идентификатор — `Id выплаты`. Наркоман: сумма-кандидат — дебетовый оборот, внешний идентификатор — номер документа, из назначения извлекаются только последние четыре цифры. Это данные preview: финансовое применение по-прежнему требует однозначной карты и отдельного подтверждения.

## Сохраняемые данные

- неизменённый оригинал в S3;
- SHA-256, размер, MIME type, filename;
- источник, отправитель и received_at;
- parser version;
- sheet name и row number;
- raw и normalized значения;
- ошибки строки;
- созданные registry/item/event IDs.
- применённая процентная ставка мерчанта с точностью до двух знаков после запятой, общая сумма реестра, вычисленная от неё комиссия и чистая сумма к возврату в preview; при подтверждении — неизменяемые параметры расчёта, сумма комиссии и чистая сумма к возврату (предложение для воспроизводимости истории).
- код и версия parser, выбранные профилем мерчанта;
- если после загрузки файла главный администратор подтвердил разовую ставку для конкретного реестра, её основание, ID реестра и автор/время одобрения; пересчитанный preview показывается главному администратору до отдельного подтверждения поступлений. Старый preview становится недействительным; одобрение ставки не публикует деньги в ledger.

## Проверки

- допустимое расширение не считается достаточной проверкой типа;
- лимит размера и количества строк;
- запрет макросов и исполнения вложенного содержимого;
- явный mapping колонок;
- обязательные merchant, card, amount и дата по согласованному формату;
- денежная сумма положительна и точно представима в `DECIMAL` с двумя знаками после запятой; исходное значение сохраняется, сумма с большей точностью не обрезается молча и требует явного решения по строке;
- карта определяется однозначно;
- totals source/accepted/rejected показаны отдельно;
- для выбранного мерчанта найден применимый тариф; до подтверждения показаны ставка, общая сумма реестра, комиссия как процент от общей суммы с двумя десятичными знаками и чистая сумма `сумма − комиссия`; промежуточный расчёт выполняется в точном decimal, итог округляется по `ROUND_HALF_UP` (`49,3856 → 49,39`; `49,3850 → 49,39`);
- ни одна строка не пропускается молча.
- при сопоставлении по ФИО исходное значение из файла сохраняется отдельно от выбранной карты; главный администратор и загрузивший реестр операционист видят рядом исходное ФИО, контакт, телефон и маску из выбранного карточного запроса;
- до подтверждения любую строку такого реестра можно вручную перепривязать только к карте выбранного запроса. Правка не изменяет исходный файл или снимок ФИО, повышает версию preview и оставляет audit event с прежней и новой картой. Ошибка суммы или структуры не может быть снята выбором карты;
- для банковского CSV отдельно показываются `Сумма операции` как кандидат суммы пополнения карты, `Комиссия Банка` и `К Перечислению`; все строки образца удовлетворяют `К Перечислению = Сумма операции + Комиссия Банка`. Банковский сбор не смешивается с комиссией «Металлиста» и не проводится в P&L автоматически до решения IMP-004;
- маскированная карта из банковского CSV не связывается с `Card` только по четырём последним цифрам. Требуется однозначное сопоставление с существующей картой через дополнительные данные или ручное подтверждение главного администратора; неоднозначная строка блокирует применение;
- полная запись PAN, банк и ФИО владельца берутся из отдельного защищённого справочника/источника, если они действительно нужны; пустые ФИО в этом CSV не заполняются догадками.

## Дубликаты

- тот же файл: checksum;
- тот же внешний реестр: merchant + external ID;
- та же строка: документированный business key;
- та же финансовая операция: downstream idempotency key.

Две строки одного реестра с одинаковой картой и суммой могут быть двумя реально отправленными банком платежами: они сохраняются как разные строки с исходными порядковыми номерами, а в банковском CSV — также с номером заказа/RRN. Совпадение карты и суммы само по себе не причина удалять строку. Повтор всего того же файла по checksum не создаёт повторного поступления без отдельной обоснованной процедуры. Надёжность номера заказа/RRN между файлами ещё проверяется.

## Применение

Если мерчант не передал пригодный для парсинга файл, главный администратор или операционист создаёт ручной реестр. Мерчант выбирается из активного справочника; каждая строка содержит выбранную активную карту, сумму в рублях и выбранный активный контакт (ФИО и телефон). Карта выбирается через поиск по маске или банку, ФИО и телефон — через отдельные поисковые поля, связанные с одной записью контакта, чтобы исключить случайное несовпадение. Разрешены 1–500 строк, в том числе повторные пополнения одной карты. Внешний номер реестра создаётся автоматически из ключа повторного запроса. Система сохраняет зашифрованный снимок введённых данных, SHA-256, автора, строки и аудит. Повтор того же запроса не создаёт второй реестр. Это ручной источник, а не исходный файл мерчанта; его нужно сверить с фактическим поступлением. Создание оставляет реестр в `preview` без проводок. Подтверждение и сторно выполняются по общему процессу реестра главным администратором.

Для первого запуска Approval выполняет главный администратор после проверки preview в модальном окне, включая автоматически рассчитанную по тарифу мерчанта комиссию и чистую сумму к возврату, и явного подтверждения фактического поступления по строкам. Операционист загружает и готовит реестр, но не публикует его и не меняет тариф. Apply выполняется транзакционно и создаёт бизнес-события, которые одновременно меняют баланс карт, чистый долг мерчанту и комиссионную выручку. Неутверждённый batch не влияет на официальный баланс. Если тариф изменился между первоначальным preview и подтверждением, незавершённый реестр пересчитывается **по новой ставке**: обновлённые комиссия и чистый долг снова показываются главному администратору до подтверждения. Запрос на подтверждение старого preview отклоняется как устаревший; применённая версия/снимок тарифа сохраняется. Исходные опубликованные проводки никогда не мутируют; назначение тарифа задним числом может скорректировать их экономический результат только через отдельный подтверждённый [перерасчёт](../accounting/retroactive-tariff-recalculation.md) и новые проводки.

При загрузке операционистом карта сопоставляется с выбранным запросом на карты либо определяется однозначно без него. Назначение карты операционисту для снятия или расхода не ограничивает загрузку ответного реестра мерчанта. После успешной загрузки интерфейс сразу обновляет список и показывает число строк, требующих исправления; оригинал файла остаётся неизменным, а денежные проводки до подтверждения не создаются.

Подтверждённый реестр главный администратор вправе сторнировать в течение трёх суток с момента подтверждения (`confirmed_at`) без удаления исходного файла, строк и проводок. Ранее подтверждённые снятия не откатываются автоматически; карта может получить отрицательный расчётный остаток. Загрузка, просмотр preview, подтверждение, применение и сторно сохраняются в аудите с автором, временем, источником и результатом.

## Дополнительные форматы Светы — 02.10.2026

Развёрнуто в production 02.10.2026: миграция 020 применена, версия parser 3. Проверки и backup — в [результате выпуска](../operations/sveta-formats-release.md).

- Прежняя карточная выгрузка XLS сохраняет mapping `Сумма`, `Номер вх.`, `По номеру карты`. Пробелы, включая неразрывные, удаляются из нормализованного номера карты; исходное значение остаётся в исходном файле и передаётся через существующую маскировку raw. Номер строки сохраняется, повторные строки не объединяются.
- Ответ XLSX распознаётся только на единственном листе `Карты к оплате` с последовательностью заголовков `№`, `НОМЕР КАРТЫ`, `ФИО`, `НОМЕР ТЕЛЕФОНА`, `БАНК`. Заголовок ищется по содержимому. В версии 3 этой структуры колонка F содержит сумму; её заголовок пустой либо `Сумма`. [Версия 5 добавляет G](#ответ-светы-с-суммами-в-g--05102026). Другие структуры не получают позиционный mapping.
- Сумма читается в точных копейках с разделителями тысяч и необязательным завершающим `₽`. Пустая, нулевая, отрицательная или некорректная сумма остаётся строкой с `invalid_amount`. Отсутствующая карта — `missing_card_reference`. ФИО и телефон не используются вместо номера карты в этом формате; внешний номер платежа в нём отсутствует.
- Пустые строки пропускаются. Строка с пустыми A/B/D/E и `оплачены успешно` в C считается итогом. Она не создаёт пополнение; итог должен быть корректным и единственным и совпадать с суммой валидных денежных строк. При ошибке суммы в строке сохраняется блокирующая ошибка preview, а сверка итога откладывается. Подпись «оплачены успешно» не является подтверждением поступления в системе.
- Формулы, макросы, PIN/CVV и неоднозначное сопоставление карт блокируются существующими проверками. Прежний формат по ФИО продолжает требовать выбранный запрос карт.

Read-only проверка приложенных образцов: XLS 30.09 — 33 строки на 5 978 267,33 ₽; его исходный `Итого` 5 920 387 ₽ расходится с суммой строк на 57 880,33 ₽. Прежний parser карточной выгрузки использует сумму строк и не проверяет исходный итог; расхождение требует отдельной сверки до подтверждения. XLSX 01.10 — 24 строки на 5 913 406 ₽, сумма совпадает с итоговой строкой. Реальные файлы не добавляются в репозиторий; тестовые структуры синтетические.

Миграцию `schema/020_sveta_response_formats.sql` применять в одной транзакции после версии схемы 18 или 19, резервной копии и проверки на отдельной тестовой БД. Для отката к старому parser остановить загрузки Светы и вернуть приложение; существующие preview нового формата остаются в истории и требуют новой версии для повторного разбора. ## Скрытые строки Светы — исправление 02.10.2026

Версия parser 4 (миграция 021 после схемы 20) исключает скрытые строки только для профиля Светы. Для XLS читаются BIFF ROW / fDyZero; библиотека xlsReader игнорировала эти метаданные. Для XLSX используется признак видимости строки. Физические номера оставшихся строк сохраняются. Сведения об исключённых непустых строках (лист, номер, `source_row_hidden`) сохраняются в `registry_upload.excluded_source_rows`, оригинал файла остаётся неизменным. Другие профили не получают новую политику видимости.

Карточные выгрузки и выгрузки по ФИО теперь сверяются с видимой строкой `Итого`, если в ней заполнена сумма. При валидных суммах платежей несовпадение отклоняет файл; неверная сумма строки остаётся блокирующей ошибкой preview. Суммы скрытых строк не входят в итог.

Предыдущая трактовка образца 30.09 как расхождения исходного итога была ошибочной: девять скрытых строк 21–29 содержат 57 880,33 ₽. Видимые 24 платежа дают ровно 5 920 387 ₽. Подтверждено на приложении и на расшифрованном сохранённом источнике с проверкой его SHA-256. [Разбор и коррекция preview](../operations/sveta-hidden-rows-20261002.md).

## Выписка Наркомана — версия 2, 09.10.2026

Mapping сохраняет XLS с одним листом, заголовками в строках 7–8 и платежами с строки 9: C — дата документа, F — номер документа, R — дебет, U — назначение. Дополнительно проверяются заголовки `Обороты`/`по дебету`, обязательный единственный `Итого:` в C с точной суммой в R и отсутствие непустых строк после итога. Сумма платежей должна совпадать с итогом; ошибка суммы остаётся блокирующей ошибкой строки. Кредитная операция не является пополнением и блокируется (`unsupported_credit_operation`); разные карточные ссылки в первой строке назначения блокируются (`ambiguous_card_reference`). Одинаковые повторные оплаты сохраняются отдельно, включая физический номер строки, лист и исходные значения. Скрытые строки для этого профиля не исключаются.

Карта получателя читается из первой строки назначения как `Карта:*1234` и нормализуется в `****1234`. Вторая строка банковского назначения содержит служебную карту/место и не используется как получатель. Новый способ сопоставления включён только для этого профиля: при выбранном запросе карт последние четыре цифры ищутся исключительно среди его различных `card_id`. Повтор одной карты в запросе не создаёт неоднозначность; две разные карты с одинаковым окончанием, отсутствие карты и принадлежность запроса другому мерчанту блокируют применение. Поиск по всем картам вместо выбранного запроса запрещён. Остальные parser сохраняют прежние правила полной карты, маски и ФИО. Без запроса сохраняется прежний поиск однозначной активной карты.

Загрузка остаётся preview без проводок. Подтверждение главным администратором, тариф, комиссия, идемпотентность, сторно и отчёты сохраняют существующие правила. Уже сохранённые источники и preview не переопределяются новой версией; ошибочный неподтверждённый preview удаляется обычным действием и файл загружается заново.
