# Жизненные циклы операций

Статус: проект
Дата: 2026-09-11

## Общий lifecycle документа

```text
draft → validated → confirmed → posted
   └────────────→ rejected
```

Фактические названия могут быть уточнены, но состояния проверки и финансовой публикации должны быть разделены.

| Состояние | Смысл | Влияет на официальный баланс |
|---|---|---|
| draft | введено человеком или parser | нет |
| validated | структура и бизнес-предусловия проверены | нет |
| confirmed | уполномоченный пользователь подтвердил факт | ещё не обязательно |
| posted | journal entry опубликован | да |
| rejected | источник признан непригодным | нет |
| reversed | опубликована связанная сторнирующая запись | да, через новое событие |

## Запрещённые переходы

- `draft → posted` без проверки и подтверждения, если операция пришла из внешнего источника;
- изменение суммы или измерений после `posted`;
- удаление `posted`;
- повторный `posted` по тому же idempotency key;
- `rejected → posted` без новой валидации.

В кабинете главный администратор может отклонить черновик с обязательной причиной. Это переводит его в `rejected`, записывает аудит и не создаёт проводок. Повторное отклонение не меняет состояние. Подтверждение суммы сверяет точные рубли и копейки, поэтому `1560000` и `1560000.00` равнозначны. Для передачи администратор может подтвердить фактически полученную сумму не больше заявленной; проверка доступных наличных у отправителя сохраняется.

## Импорт

```text
received → parsed → validated → previewed → approved → applied
```

Повторный парсинг создаёт новую попытку с parser version и не перезаписывает исходный результат.

## Reversal

```text
original posted
      ↓
reversal posted
      ↓
replacement posted, если нужен
```

Все три записи связаны, имеют автора, время и причину.

Для подтверждённого реестра главный администратор может выполнить reversal в пределах трёх суток с момента его подтверждения (`confirmed_at`). Если реестр уже получил тарифные корректировки, его откат автоматически создаёт сторно исходной записи и **всех** связанных корректировок в одном согласованном пакете; после этого комиссия и долг отменённого реестра равны нулю. Дополнительное подтверждение каждой корректировки не требуется. Исходные публикации не редактируются и не удаляются. Каждое действие и попытка запрещённого перехода фиксируются в [журнале аудита](../security/audit-log.md).

Изменение тарифа задним числом — отдельный lifecycle, не откат реестра: `draft изменения → preview перерасчёта и баланса → подтверждение главным администратором → корректирующие postings`. До подтверждения ledger не меняется. Исходные проводки реестров не редактируются; все затронутые финансовые последствия исправляются новыми связанными записями. Техническое предложение: если входные данные изменились после preview, потребовать новый расчёт и подтверждение. [Правило перерасчёта](../accounting/retroactive-tariff-recalculation.md).

Исправление ручной разовой ставки после подтверждения конкретного реестра разрешено главному администратору. Это отдельный lifecycle, не смена общего тарифа и не откат реестра: `draft исправления → preview старых/новых сумм и баланса до/после → явное подтверждение главным администратором → связанные корректирующие postings`. До подтверждения ledger не меняется; исходные опубликованные postings не редактируются. Разница комиссии относится к месяцу подтверждения исходного реестра по Москве; ранее утверждённый отчёт требует повторного утверждения бухгалтером после корректировки.
