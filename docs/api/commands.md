# Команды приложения

Статус: проект
Дата: 2026-09-11

Web, Telegram и import workers вызывают одинаковые application commands.

## Первоначальный каталог

- `CreateMerchant`
- `RegisterCard`
- `CreatePaymentContact` (ФИО и телефон в справочнике; в demo только синтетические значения)
- `CreatePaymentRequest` (плановые строки с обязательным `contact_id` и снимком ФИО/телефона; без ledger)
- `ExportPaymentRequestXLSX` (повторная выдача ранее сформированного файла после проверки SHA-256)
- `SetCardLimit`
- `CreateMaterialBatch`
- `UploadRegistry`
- `SetRegistryOneOffRate` (проектное имя: главный администратор назначает и подтверждает разовую ставку уже загруженному реестру до подтверждения поступлений; обновляет preview, не ledger)
- `PreviewRegistryManualRateCorrection` и `ConfirmRegistryManualRateCorrection` (проектные имена: исправление ручной ставки уже подтверждённого реестра; первая команда показывает финансовую разницу и баланс до/после без postings, вторая после явного подтверждения главного администратора создаёт связанные корректирующие postings)
- `ApproveRegistry`
- `ApplyRegistry`
- `ConfirmMerchantFunding`
- `RecordWithdrawal`
- `RecordCardBalanceObservation`
- `CreateCashHandover`
- `ConfirmCashHandover`
- `RecordMerchantRepayment`
- `ConfirmCashSurplusResolution` (проектное имя: главный администратор классифицирует подтверждённый излишек; для денег мерчанта переводит невыясненное обязательство в отдельный долг этому мерчанту, не списывая наличные)
- `ConfirmMerchantSurplusReturn` (проектное имя: подтверждает отдельную фактическую выдачу найденных денег мерчанту; списывает наличные и погашает только долг по связанному излишку, не обычную кредиторку по реестрам)

- `ConfirmRetroactiveTariffRecalculation` (проектный command; явное подтверждение главным администратором и корректирующие postings)

## Общий command envelope

- command_id / idempotency_key;
- actor_user_id;
- occurred_at;
- source_document_id;
- payload;
- reason/comment;
- expected version для конкурентных изменений.

Command handler валидирует права и состояние, сохраняет business event и вызывает ledger в одной транзакции, когда событие должно быть опубликовано.

Для новых обычных расходов кабинет передаёт категории `agent_fee`, `bank_fee`, `salary`, `warmup`, `it_infrastructure`, `taxes`, `communication`, `delivery`, `other`. Сервер не принимает `repayment`, `losses` и `dividends` как категорию `RecordExpense`: первая относится к `RecordMerchantRepayment`, вторая — к отдельному списанию подтверждённой недостачи, третья ожидает самостоятельного правила распределения капитала. Старые категории `operating` и `transport` читаются и могут завершаться для уже подготовленных черновиков.

`GET /api/catalog` для главного администратора и операциониста включает `request_cards`: активные карты в порядке распределения строк с `bank` и `full_name`/`phone` из последнего снимка реестра по карте. Поля независимы в форме; перед формированием XLSX новые комбинации сохраняются через `payment_contact`. Повторная комбинация возвращает существующий активный контакт без UPDATE и без расширения прав прикладной роли.

В `GET /api/catalog` записи `banks` включают `source` и `selectable`. Для новой карты интерфейс показывает только доступные записи и ищет по названию. `POST /api/catalog/create` с `kind: "card"` повторно проверяет доступность выбранного `bank_id` на сервере. Команда `platform sync-nspk-banks` получает полный перечень с официального сайта НСПК и атомарно обновляет справочник; `card_id`, PAN и проводки не меняются.

`POST /api/payment-request/create` принимает `mode: "cards"`, `merchant_id`, `external_ref` и от 1 до 500 `rows` с `card_id` и `contact_id`. Сервер проверяет действующие карты и контакты, уникальность карты внутри запроса и отклоняет поля суммы. `GET /api/payment-requests` и `GET /api/payment-request/rows` возвращают состав карт без плановых сумм. XLSX нового запроса содержит реальные полные номера из зашифрованного хранилища и не содержит сумму: её назначает мерчант в ответном реестре. Экспорт формируется при скачивании, не сохраняется открытым файлом и оставляет запись аудита. Карта без полного номера не допускается в запрос. Исторические запросы и файлы не переписываются. Автоподбор по количеству выполняется в интерфейсе и передаёт в API такой же явный состав. `POST /api/catalog/create` для `kind: "card"` доступен главному администратору и операционисту, принимает `bank_id`, `owner_label` и `pan`, выводит из номера маску и хранит его в зашифрованном хранилище. Дозаполнение номера ранее заведённой карты через `POST /api/card/pan` удалено как устаревший сценарий. `POST /api/card/pan/replace` позволяет главному администратору и операционисту исправить номер карты без истории использования: требуются `card_id`, `expected_mask`, новый `pan` и `reason`. API не возвращают полный номер.

Для страницы «Карты к оплате» `GET /api/payment-requests?page=N` возвращает `items`, `page`, `total`, `has_more` (50 записей на страницу); прежний вызов без `page` сохраняет массив для существующих потребителей. `GET /api/payment-request?id=UUID` возвращает одну запись. Поле `title` отделено от номера `external_ref`: при создании пустое название заменяется номером, при редактировании непустое название сохраняется вместе со строками и версией запроса.

Список «Операции» использует `GET /api/drafts` с необязательными `page` (100 записей на страницу), `kind`, `source`, `recipient`, `amount_from`, `amount_to`, `date_from`, `date_to`. Участники передаются как `card:UUID`, `custodian:UUID`, `merchant:UUID` или `category:код` согласно полю. Диапазон дат включителен; для расходов используется дата из черновика, для остальных операций — дата создания по Москве. Операционист получает только свои разрешённые черновики, в том числе при фильтрации; `GET /api/drafts?id=UUID` сохраняет прежнюю проверку доступа.

## Редактирование справочников

`POST /api/catalog/update` принимает `kind` (`bank`, `card`, `payment_contact`, `custodian`, `drop_handler`), `id` и только разрешённые описательные поля. Главный администратор меняет вручную заведённые банки, карты любого статуса, активные контакты и имена активных ответственных; операционист — карты любого статуса и активные контакты. Банк НСПК, полный номер карты и функция ответственного этим запросом не изменяются. Статус карты и дроповод меняются по контракту схемы 026 ниже. Успешное изменение записывается в аудит. Сценарий дозаполнения полного номера существующей карты удалён; ранее сохранённые номера и отдельное исправление номера не затронуты.

Табличный `GET /api/payment-requests?page=N` возвращает 15 запросов на страницу. Табличный `GET /api/drafts?page=N` загружает 15 операций и одну дополнительную для определения наличия следующей страницы; интерфейс показывает 15 и сохраняет применённые фильтры при переключении страниц. Запрос с `id` по-прежнему возвращает отдельную запись.

## Фильтры реестров оплат

`GET /api/registries?page=N` возвращает `{items, page, has_more}`: 15 записей в порядке создания (новые сначала, при равенстве — по ID). Необязательные фильтры: `q` (буквальное вхождение без учёта регистра в номер или `external_ref`), `merchant_id`, `status` (`preview`, `posted`, `reversed`), `date_from`, `date_to` (включительные границы даты фактических оплат `payment_date`, YYYY-MM-DD). Некорректные даты, обратный диапазон, неизвестный статус или страница вне 1–10000 возвращают 400. Без `page` сохраняется прежний массив до 100 записей; запрос с `id` возвращает отдельный реестр и игнорирует фильтры списка. Удалённые записи исключены; операционист по-прежнему видит только загруженные им реестры. Фильтры применяются до ограничения выдачи.

В кабинете фильтры применяются кнопкой «Показать», сбрасывают страницу на первую и сохраняются при пагинации. На телефоне панель раскрывается кнопкой «Фильтры». Пустой результат фильтрации отличается от отсутствия реестров.

## Карты и дроповоды (схема 026)

`GET /api/catalog` дополняет каждую карту `drop_handler_id: UUID|null` и `drop_handler_name: string|null`, добавляет массив `drop_handlers: [{id,name,active}]` для существующих потребителей справочников (кроме роли collector, которой возвращается только список карт). Поле `owner_label` сохраняет значение ФИО держателя. Статус карты — `active|limit|blocked|retired`; справочник карт включает неактивные записи, `request_cards` по-прежнему только активные.

`POST /api/catalog/create` с `kind=card` требует `drop_handler_id` действующего дроповода вместе с прежними `bank_id`, `owner_label`, `pan`. Успех 201 `{id}`, ошибка выбора 400, запрещённая роль 403. `POST /api/catalog/update` с `kind=card` принимает прежние `id`, `owner_label`, а также необязательные `drop_handler_id` и `status`. Отсутствие ссылки сохраняет прежнюю; NULL или пустая строка очищает её; повторный выбор прежнего отключённого дроповода сохраняется. Успех 200 `{id}`. Права остаются у chief/operator.

`kind=drop_handler`: создание принимает `name`; редактирование — `id`, `name`, `active` (boolean или строка из web-формы). Отсутствие active при редактировании сохраняет прежнюю активность. Управление доступно chief; физического удаления нет. Справочник, назначение и смена статуса аудируются. [Семантика статусов](../to-be/cards-and-limits.md#дроповод-и-операционный-статус--согласовано-17102026).

## Telegram: личная выдача мерчанту

`/repay` доступна только Тони в личном чате. Интерактивный выбор из названий активных мерчантов (10 на странице) → сумма → личное подтверждение. Источник — наличные Тони; выдача сверх долга разрешена как дебиторка мерчанта. `/cancel` отменяет только личный ввод и его неподтверждённую выдачу. Подробности, доступ и очередь уведомлений — в [Telegram](../integrations/telegram.md#личная-выдача-мерчанту-тони--21102026). Нового HTTP API нет; попытка web-подтверждения этого черновика возвращает 409.


Для Telegram-адаптера `card_status`/`block_card` с версии 028 поддерживают команду без параметров и отдельное последующее сообщение в активном пользовательском диалоге. Однострочный контракт и web API неизменны. Ответ после успеха содержит последние 4 цифры и установленный статус; подсказка не является ошибкой формата. [Шаги и защита повторов](../integrations/telegram.md#пошаговая-смена-статуса-карты--исправление-21102026).

## Ручной реестр оплат со связью с запросом карт

`POST /api/registry/manual`, роли `chief` и `operator`: прежние поля `merchant_id`, `payment_date`, `idempotency_key`, `rows` сохраняются. Необязательное поле `payment_request_id` включает связанный ввод; тогда обязательна целочисленная `payment_request_version` из `GET /api/payment-request?id=…`. Каждая отправленная строка содержит `card_id`, целочисленный `payment_request_row_no` из `GET /api/payment-request/rows?id=…` и положительную `amount` в рублях. `contact_id` для связанного ввода не требуется: сервер использует сохранённый снимок контакта строки запроса. Форма не отправляет строки с пустой суммой; API отклоняет пустые и нулевые суммы и пустой список оплат. Несоответствие мерчанта, недоступный запрос или карта вне указанной строки дают `400`, устаревшая версия — `409`. Без `payment_request_id` действует прежний контракт с обязательным `contact_id`.

Связь сохраняется вместе с зашифрованным источником, строками и аудитом в одной транзакции; идентификатор и версия запроса входят в снимок источника и проверку повторного запроса. Ответ `201` содержит `id`, `rows`, `accepted_total`; повтор того же запроса возвращает `200` с прежним `id` и `status=already_created`. Изменённые данные с прежним ключом дают `409`. До подтверждения реестр остаётся в `preview`, проводки не создаются. Схема БД не меняется: используется существующее поле `registries.payment_request_id`.

## Подтверждение реестра через web и Telegram — 27.10.2026

`confirmRegistryCommand(tx, actor, input, channel)` — общая типизированная команда одного Go build. Поля `id`, `version`, `confirm_total`, `confirm_commission`, `confirm_rate_bp` имеют прежние точные строковые значения; результат `posted`/`already_posted` либо код и ошибка. Caller проверяет полномочия, Telegram дополнительно проверяет получателя и неизменяемый preview, затем владеет commit/rollback. Даты, ручной тариф, нормализация долга, audit actor/channel и ключ `registry:<id>` одинаковы для обоих adapters. Новый публичный HTTP endpoint не вводится.
